# QDR 数据仓库管理模块 V1.0 实施方案

> 版本：V1.0  
> 编写日期：2026-11-17  
> 基线：`main` / `ed856e58306608ec0efbfa4a5090ae34b4712ee1`  
> 状态：实施方案，尚未包含页面或 API 代码变更  
> 目标：在 QDR V4 中新增独立「数据仓库」工作区，提供数据资产、更新状态、质量问题和真实样本的可视化管理。

---

## 1. 产品目标与边界

### 1.1 目标

数据仓库页面要让用户在一个入口内快速回答五个问题：

1. 当前仓库实际维护了哪些数据？
2. 每类数据最新观测到什么时候，最近什么时候抓取、写入？
3. 数据覆盖哪些证券、日期、指标或事件？是否存在明确缺口？
4. 数据来源、原始回执、字段和使用资格是否可信？
5. 当前有哪些失败、过期、缺失或尚未满足的依赖，需要处理什么？

页面定位为 **Data Warehouse & Observability**，由「运行健康驾驶舱」和「数据资产浏览器」组成。

### 1.2 非目标

V1 不做以下工作：

- 不新建中央数据库，不复制行情或原始数据。
- 不接入新的供应商，不购买数据，不自动扩大历史证券范围。
- 不在页面打开或刷新时自动拉取外部数据。
- 不提供任意 SQL、数据库写入、数据删除、回补或供应商重试。
- 不因为数据已采集、最新或页面显示正常，就提升 PIT、模型、预测或交易资格。
- 不以六大体系覆盖率、特征实现率等百分比作为首屏核心指标。

所有数据维护和回补操作继续走现有数据维护工具与 CLI。

## 2. main 分支现状与需要复用的能力

本方案按当前 main 代码结构制定，不按生成图中的虚构数字制定。

### 2.1 现有页面结构

- 主工作台入口：`src/quant_research/v4_shell.html`
- V4 页面注册与导航：`src/quant_research/assets/v4_ui_core.js`
- 当前数据中心页面：`src/quant_research/assets/v4_ui_pages_c.js` 中的 `pages.data`
- V4 页面样式：`v4_shell.html` 引入的 V4 样式文件
- API 路由：`src/quant_research/web.py`

当前 `pages.data` 主要展示研究就绪度、四层资格和数据新鲜度；它不是完整的数据资产浏览器。因此新建 `pages.warehouse`，不覆盖现有页面。

导航建议：

- 新增「数据仓库」：数据资产、来源状态、数据预览、质量问题。
- 现有「数据中心」改为「数据资格」或保留原名：研究准入、PIT 资格、模型可用性。
- 原 `/data` 高级数据维护工具继续保留，作为维护、冻结、审计和回补入口。

### 2.2 现有数据资产目录

`src/quant_research/data/catalog.py` 当前登记：

- 6 个有明确物理数据库/数据表的资产；
- 4 个当前受阻或尚未具备资格的资产；
- 因子实验登记、冻结行情观察、策略版本、每日观察报告等 4 个研究类资产。

当前目录共约 14 个逻辑资产，实际数量以运行时目录为准。

已知需要补入统一资产视图的存储：

1. L1 市场观测数据库：`data/l1_market/market_data.duckdb`。
2. Alpaca 当前证券目录归档：`data/managed/asset_observations/`。

L1 数据库包含行情 Bars、证券池观察、市场指标观察、个股特征、跨资产参考序列、事件、数据源健康、质量检查、未来路径标签及原始回执等表。页面应把它们作为同一物理数据库下的逻辑数据资产/数据表展示，不能漏掉。

### 2.3 现有数据源与研究注册表

- L1 数据目录：`src/quant_research/data/l1_market_catalog.py`
- 当前注册：6 个体系、12 个维度、109 个特征定义、21 个数据源定义。
- 实际源运行情况保存在 L1 数据库的 `l1_market_source_health`；不是所有注册源都已真实采集。
- 维护任务记录：`outputs/maintenance/<run_id>/manifest.json`。
- 原始请求与回执：`data/raw/receipts/`、`data/raw/objects/`，以及 Yahoo 对应缓存目录。
- 数据目录快照：`data/catalog/latest.json` 与不可变快照目录。

注册状态与运行状态必须分开显示。例如，注册为 `IMPLEMENTED_PARTIAL` 不等于今天成功更新；没有运行记录应显示「尚无运行观测」，不能伪装成正常或故障。

### 2.4 关键只读约束

**不能直接在新 GET 接口里调用 `market_data_snapshot()` 作为只读实现。**

当前该函数会实例化 `L1MarketStore`；其构造函数会创建目录、打开可写 DuckDB 连接并执行 schema 初始化。新数据仓库页面必须使用独立只读读取器：

- 数据库文件不存在时直接返回未创建状态，不创建文件或目录。
- DuckDB 使用 `read_only=True`。
- SQLite 使用 URI `mode=ro`。
- 只读取已存在的表，不执行 DDL、初始化或写入。
- 维护锁生效时，返回明确的「维护中」状态，不与写任务竞争。

另外，现有 `build_catalog()` 会扫描并校验原始回执对象的 SHA256，成本可能随缓存增长。页面每次打开不应无条件执行全量原文哈希审计。应给目录构建增加可选的轻量模式，保留 CLI 原有完整审计默认行为。

## 3. 页面信息架构

### 3.1 首屏：运行概况

首屏只放能帮助用户判断当前情况的指标：

| 指标 | 定义 |
|---|---|
| 数据资产 | 当前目录中登记的逻辑资产数量 |
| 已有真实记录 | 至少存在真实数据/版本/归档的资产数量；不代表可用于预测 |
| 需要关注 | 当前可证实的阻断、过期、缺失、质量或回执异常数量 |
| 最近成功维护 | 最近一次整体成功的维护完成时间；没有成功记录则显示「暂无」 |

顶部同时显示目录快照生成时间、当前维护状态和「刷新状态」操作。

「刷新状态」只重新读取本地数据和运行记录，不触发外部供应商请求。跳转到现有 `/data` 才能执行维护任务。

### 3.2 需要关注

位于首屏 KPI 下方，按严重程度排序：

1. BLOCKED / FAILED：数据源或任务明确失败。
2. STALE：超过对应频率的允许新鲜度。
3. MISSING：本应存在但当前缺少实际记录。
4. PARTIAL：任务或数据覆盖明确不完整。
5. 限制说明：历史 PIT、身份、许可或使用资格未满足。

每个问题至少展示：

- 问题名称和状态；
- 实际错误码/缺失原因；
- 最近发生时间；
- 影响的数据集或来源；
- 已有证据支持的下游影响；
- 可执行的下一步（如检查凭据、进入维护页、查看回执）。

不得根据猜测推导影响范围。只有存在明确依赖关系时才显示下游模块。

### 3.3 数据资产列表

数据资产是页面主体，不按六大体系拆成重复的覆盖率卡片。

支持搜索、分类、状态筛选。首批分类：

- 行情数据
- 市场指标
- 因子数据
- 宏观与跨资产
- 公司与证券数据
- 研究与归档

六大 L1 体系仅作为关联标签或辅助筛选条件；不显示无明确业务意义的覆盖率环形图。

列表字段：

- 数据集名称、所属分类/体系；
- 数据来源；
- 实际存储位置与表名；
- 物理记录数（如适用）；
- 唯一证券数/证券日数/指标数（按数据集类型提供）；
- 数据起止范围；
- 最新观测日期；
- 最近抓取/写入时间（只有实际记录才展示）；
- 更新频率；
- 数据状态和使用限制。

必须区分物理行数与去重后的业务样本数。例如行情表可能保留多个原始修订版本，物理行数不能直接当成证券日样本数。

### 3.4 数据集详情

桌面端采用右侧详情面板；窄屏改为下方详情区或独立详情视图。

详情分为五个 Tab：

1. **概览**：来源、存储位置、表名、数据范围、物理行数、唯一键数量、最新观测时间、最近抓取时间、更新频率、使用政策。
2. **数据预览**：真实样本、筛选条件、分页；展示原始版本时间及回执标识（如适用）。
3. **字段结构**：字段名、类型、单位、空值情况、主键/唯一键说明。
4. **更新记录**：相关维护任务、开始/结束时间、状态、插入数、缺失区间、错误原因。
5. **血缘与资格**：来源 → 原始回执 → 权威存储 → 派生特征/下游模块；展示 PIT、研究、预测资格及明确限制。

没有可查询关系的数据资产应明确标记「无结构化样本预览」，提供其真实 manifest、版本或归档信息；不强行把所有资产伪装成 SQL 表。

### 3.5 数据源监控与维护历史

首屏资产详情之外，增加两个可折叠/下方区域：

- 数据源监控：注册状态、运行状态、最新观测日期、可用时间、抓取时间、最近错误码、频率和限制说明。
- 维护历史：最近若干次真实 manifest，展示整体状态及每个任务组的结果。

## 4. 状态、实时性与资格规则

### 4.1 状态必须分层

| 层级 | 示例状态 | 含义 |
|---|---|---|
| 资产存在性 | COLLECTED / NOT_CREATED / BLOCKED | 是否真实存在数据或归档 |
| 任务运行 | UPDATED / RUNNING / BLOCKED / FAILED | 最近一次任务实际结果 |
| 数据新鲜度 | CURRENT / STALE / UNKNOWN_DATE / NOT_EVALUATED | 按数据频率评估 |
| 数据质量 | PASS / PARTIAL / FAILED / UNKNOWN | 实际校验结果 |
| 使用资格 | OBSERVATION_ONLY / ATTRIBUTION_ONLY / PIT_UNVERIFIED 等 | 允许用于什么用途 |

不得把这些状态压成一个绿色「正常」标签。

### 4.2 时间字段

数据集/数据源尽可能分别展示：

- Observation Date：数据实际描述的日期；
- Published / Available At：供应商发布或数据首次可用时间；
- Fetched At：本地实际获取时间；
- Ingested At：实际写入仓库时间。

只有观测日期、没有抓取时间的资产，显示「观测日期已知，抓取时间未记录」，不得把日期当作实时更新时间。

### 4.3 新鲜度规则

- 复用 `data/l1_market_freshness.py` 的频率容忍策略，但不把「CURRENT」解释为交易所盘中实时。
- 日频、周频、月频和事件数据分别判断，不用统一的 24 小时阈值。
- 周末、节假日和供应商发布滞后需要遵循对应频率。
- `current_v4_freshness()` 只描述其覆盖的核心 ETF/模块状态，不作为所有数据集的通用新鲜度算法。
- 没有时间证据时返回 UNKNOWN / NOT_EVALUATED，而不是自行推断。

### 4.4 资格边界

- `COLLECTED_RESTRICTED_USE` 表示已采集但用途受限，不等于预测可用。
- 当前 Alpaca 证券目录不是历史 PIT 股票池。
- French 因子当前为归因/描述用途，不能自动提升为历史决策输入。
- SEC 财务候选不是已验收 PIT 财务。
- L1 未来路径标签是结果验证数据，不是预测输入。
- 页面不允许修改任何资格字段或把限制状态人工改绿。

## 5. 后端实现方案

### 5.1 新增服务

新增：

`src/quant_research/data/warehouse_observability.py`

职责：

- 读取现有数据资产目录；
- 读取 L1 数据库的表级统计和最新来源健康记录；
- 读取维护 manifest；
- 生成统一问题列表；
- 读取单个资产详情、字段结构和安全样本；
- 统一处理不存在、维护中、权限受限和数据损坏状态。

服务只负责读取和归并，不采集外部数据，不写数据库。

### 5.2 资产目录补充

在 `src/quant_research/data/catalog.py` 中：

1. 为 `build_catalog()` 增加可选轻量模式，默认完整行为不变；完整 CLI 仍执行原始回执哈希校验。
2. 新增 L1 Market Store 的只读资产检查，展示同一 DuckDB 中的表级记录数、日期范围和最新时间。
3. 增加 Alpaca 当前证券目录归档资产（如果实际快照存在）。
4. 不将「计划中」资产误记为已采集，不把 excluded/legacy 数据库升级为正式输入。

### 5.3 API 契约

全部为 GET，只读接口：

| 接口 | 作用 |
|---|---|
| `GET /api/v1/warehouse/overview` | KPI、数据资产、问题列表、来源健康、最近维护 |
| `GET /api/v1/warehouse/datasets/{dataset_id}` | 单个资产详情、字段、范围、资格、血缘 |
| `GET /api/v1/warehouse/datasets/{dataset_id}/preview` | 指定资产的真实样本和分页 |
| `GET /api/v1/warehouse/runs?limit=20` | 最近维护任务 manifest |

`overview` 返回建议结构：

- `generated_at_utc`
- `catalog_generated_at_utc`
- `summary`
- `datasets[]`
- `attention[]`
- `sources[]`
- `maintenance.latest`
- `maintenance.recent_runs[]`
- `policy.read_only=true`

每个 dataset 至少包含：

- `dataset_id`、`name`、`category`、`systems[]`
- `source`、`path`（仅相对路径）、`table` / `tables[]`
- `status`、`cadence`、`use_policy`、`missing_reason`
- `physical_rows`、`unique_rows`、`symbols`（适用时）
- `first_observation`、`last_observation`
- `latest_available_at_utc`、`latest_fetched_at_utc`、`latest_ingested_at_utc`
- `preview_supported`、`limitations[]`

### 5.4 数据预览白名单

初期支持已有权威结构化数据：

- `market_prices`：`data/real_v21.duckdb / prices_daily`，严格限定 ALPACA / SIP / raw。
- `yahoo_research_prices`：`data/research.duckdb / prices_daily`，严格限定 YAHOO / yahoo / yahoo_split_adjusted 及既定研究窗口。
- `corporate_actions`：`corporate_event_versions`。
- `sec_filings`：`filing_index_versions`。
- `sec_candidates`：`financial_candidates`，明确展示 decision_eligible=false。
- `classic_factors`：`factor_returns`，严格限定 KEN_FRENCH / ATTRIBUTION_ONLY。
- L1 数据库：通过固定资源映射访问 bars、observations、security_features、reference_series、source_health、quality_checks、events、path_labels 等已存在表。

因子实验、策略、冻结快照、每日观察等资产按其实际结构提供版本/manifest/JSON 摘要；不支持的资产返回明确的 `PREVIEW_NOT_SUPPORTED`，不能拼接任意 SQL。

### 5.5 查询安全

- dataset_id、L1 resource/view 均使用代码内白名单映射。
- SQL 表名、字段名和过滤模板不能由前端任意指定。
- 用户输入只作为参数绑定值。
- limit 最大 50；offset 有上限；日期必须是 ISO 日期；证券代码限制长度和字符集。
- 文件路径必须 resolve 后仍位于项目数据根目录。
- DuckDB/SQLite 只读连接；不允许 API 写入或创建数据库。
- 不返回凭据、环境变量或绝对机器路径。
- 维护锁期间不并发读取正在写入的同一数据库。

### 6.4 视觉约束

沿用当前 V4 浅色研究工作台、深色侧栏和蓝紫强调色。重点是信息层级与可读性：

- 「需要关注」优先级高于分类统计。
- 数据集列表是主区域，不使用大量大卡片。
- 状态标签统一、克制，错误和阻断才使用高注意力颜色。
- 数据详情中的时间、来源、行数、限制说明要清晰。
- 不使用示意行情曲线或假样本；无数据就显示真实空状态。
- 不再使用六个 98%/99% 覆盖率圆环。

## 7. 开发任务拆分

### P0：页面与只读数据链路（首个交付）

1. 新增只读仓库观测服务。
2. 补全 L1 数据库与当前证券目录资产登记。
3. 新增 overview、dataset detail、preview、runs API。
4. 在 V4 中新增数据仓库导航和页面。
5. 完成数据资产列表、问题列表、数据详情和真实样本预览。
6. 完成数据源新鲜度和最近维护状态展示。
7. 完成后端与页面回归测试。

### P1：可观测性增强

1. 字段空值率、异常值及 schema 差异。
2. 数据集与来源之间的血缘映射。
3. 历史维护任务对比和数据量变化。
4. L1 维度/特征的状态下钻（只显示真实观测，不显示虚假覆盖率）。
5. 回执校验历史及失败对象定位。

### P2：后续运维能力（本次不做）

- 经确认的单任务重试；
- 指定数据区间回补；
- 维护策略配置；
- 条件预警。

P2 涉及写操作，必须独立设计权限、锁、幂等、审计和确认流程，不能混入本次只读页面。

## 8. 测试与验收标准

### 8.1 后端测试

- 不存在的数据目录/数据库不会被 GET 创建。
- DuckDB 以 read-only 打开；SQLite 以 mode=ro 打开。
- L1 数据库不存在时返回明确空状态，不调用 `L1MarketStore` 初始化。
- 维护锁期间返回维护中，不产生并发写读。
- dataset_id、resource、日期、limit、offset 非法时返回 400/404。
- 任意 SQL、任意表名和路径穿越均不可执行。
- 数据预览严格遵循来源/价格口径过滤。
- 物理行数与唯一证券日数量分别计算。
- 无 available_at/fetched_at 时不推断实时性。
- 没有 source_health 记录时返回 NOT_OBSERVED，而不是 CURRENT。
- 任何 API 响应都不修改 PIT、预测、交易或订单资格。

### 8.2 前端测试

- V4 导航可进入、返回、刷新 warehouse 页面。
- 无数据、目录缺失、维护中、接口失败、无预览权限都有明确空状态。
- 搜索、分类、状态筛选、资产切换、预览分页正常。
- 不出现硬编码的资产数量、证券数、更新日期、成功率或样本行。
- 原 `pages.data`、四层页面和 `/data` 维护工具不回归。

### 8.3 验收标准

V1 完成必须同时满足：

1. 页面展示的是当前 main 真实登记/真实存储的资产，而不是设计稿的 42 个虚构数据集。
2. 能看到数据源注册状态与真实运行状态的区别。
3. 能看到观测日期、可用时间、抓取时间、写入时间；缺少证据时明确显示未知。
4. 能识别阻断、过期、缺失、部分失败和使用限制，并说明实际原因。
5. 至少核心行情、经典因子、公司行为、SEC、L1 观测数据可以查看真实样本或表级记录。
6. 所有预览均有来源、筛选范围、分页和只读边界。
7. 页面刷新不会触发供应商采集或改变数据。
8. 现有四层研究、数据资格和维护任务均保持原行为。
9. 所有新增测试通过，现有相关测试无回归。

## 9. 推荐工程交付方式

本功能作为一个完整模块交付，不拆成多个相互依赖的小 PR：

1. 先实现只读服务、资产目录补齐和 API。
2. 再实现 V4 页面、导航、样式与交互。
3. 补齐测试并运行完整相关测试集。
4. 对照预览图做 UI 验收。
5. 一个功能 PR 统一提交到 main，审核通过后合并。

本文件只确立实现范围和验收口径；当前不修改数据源、不重建数据库、不运行维护任务，也不改变任何模型资格。
